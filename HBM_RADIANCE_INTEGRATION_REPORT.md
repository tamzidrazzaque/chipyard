# HBM / Radiance Integration Report

First end-to-end validation of Radiance-generated memory traffic through the
real Radiance cache/memory hierarchy into the FASED HBM2 timing model, on a
single memory channel, with request tracing and Ramulator timing-legality
checking. PARE-controller work is explicitly out of scope (RTL not yet
available; blocked on Agustin).

## 3. Actual elaborated Radiance → HBM path

Verified in the elaborated FIRRTL
(`sims/firesim-staging/generated-src/firechip.chip.FireSim.FireSimRadianceMemPerfConfig/`):

```
16x TLTrafficGen            (per-lane pattern generators, radiance/unittest/TLTrafficGen.scala)
  -> CoalescingUnit         (real Muon coalescer, MemPerf.scala reuses MuonTile wiring)
  -> TLULNBDCache           (L0d) -> TLFragmenter/TLWidthWidget
  -> TLNBDCache             (cluster L1, RadianceCluster.scala)
  -> clsbus -> AddressScopeNode(0..2GiB) -> MMIOAddressOrNode(| 0x1_0000_0000)
  -> csbus -> system bus -> InclusiveCache (SiFive L2) -> memory bus
  -> AXI4 memory port (AXI4IdIndexer/AXI4UserYanker)
  -> FASED bridge -> HBMModel (HBM2, 2 pseudo-channels, FR-FCFS)
```

The MemPerf tile replaces only the Muon core with traffic generators; the
coalescer, L0d, cluster L1, L2 and memory bus are the real Radiance hierarchy
(`MemPerfMuonTile`, radiance `unittest/MemPerf.scala`).

## 4. Single memory channel

- `RadianceBaseConfig` carries `WithNMemoryChannels(1)`; the elaborated DTS
  shows a single `memory@80000000` region (`reg = <0x0 0x80000000 0x1 0x0>`,
  i.e. 4 GiB).
- The Golden Gate driver header (`FireSim-generated.const.h`) contains exactly
  one `registry.add_widget(new FASEDMemoryTimingModel(...))` — one FASED HBM
  timing-model instance, i.e. genuinely single-channel.

## 5. Verified end-to-end address mapping

Chain re-proven in the integrated system (source + observed trace):

1. Producer: `TrafficPatterns.getDmem(0)` issues GPU-local
   `0x100_0000 + offset` (`TrafficPatterns.scala`), bounded to 1 MiB.
2. Coalescer/L0d/L1 pass addresses unchanged (33-bit GPU-local space,
   `TLNBDCache.scala:59`).
3. Cluster egress ORs in the GPU DRAM base: `MMIOAddressOrNode(default =
   gmemAddr.U)` with `GPUMemory = (0x1_0000_0000, 2 GiB)`
   (`RadianceCluster.scala:115-123`, `radiance/subsystem/Configs.scala:547`).
4. L2/MBus/AXI4 pass the full physical address through; ExtMem spans
   `0x8000_0000 .. 0x1_8000_0000`.
5. The FASED bridge and `HBMModel` receive the address **unchanged**; observed
   first request `HBMREQ ... addr=0x1_0100_0080` = `0x1_0000_0000 | 0x100_0000
   | 0x80` exactly.

Decode used by the model's scheduler (runtime-programmed by
`hbm2-FRFCFS-2400-OP-REFab.conf`; the trace's pc/bg/bank/row are the model's
own decode registers, so this is authoritative):

| Address bits | Field | Runtime register |
|---|---|---|
| `[5:0]` | byte offset in 64 B access | (implied by line size) |
| `[9:6]` | column (line in row) | derived, `parse_hbm_req_trace.py` |
| `[13:10]` | bank (bank[1:0] = bank group) | `+mm_bankAddr_offset=10 mask=15` |
| `[14]` | pseudo-channel | `+mm_pcAddr_offset=14 mask=1` |
| `[33:15]` | row | `+mm_rowAddr_offset=15 mask=524287` |

The 19-bit row field covers address bit 33, so the GPU window's bit 32 lands
in row bit 17 (`0x20000`) — observed rows `0x20200..0x2021F` for the 1 MiB
MemPerf footprint. All 34 address bits are captured (6+4+1+19 + 4 column);
no configuration change was needed for Radiance's layout. The previously
reported bit table is confirmed.

## 6. Workloads run (single 24 M-cycle run, patterns execute back-to-back)

`FireSimRadianceMemPerfConfig` runs the radiance `dmemPatterns` list in order,
16 lanes × 4096 requests per pattern instance, each pattern in write-then-read
variants, bounded to a 1 MiB window (`TrafficPatterns.scala`): 16 strided
(warp/lane stride grid × 4 B/2 B), 4 random, 5+5 tiled/transposed, 5+5
swizzled/transposed-swizzled. Within the 24 M-cycle budget the run covered the
full strided and random blocks and a large portion of the tiled/swizzled
blocks (62 observable pattern segments; the pattern list would need ~2-3x more
cycles to complete — rerun with a larger `+max-cycles` for full coverage).

Aggregate (from `analyze_hbm_req_trace.py`, segments in
`sims/firesim/sim/scripts/hbm-validation/examples/radiance-memperf-segments.txt`):

- **613,255** HBM requests accepted (R=396,263 / W=216,992 — writes appear
  during read patterns and vice versa via L1/L2 fills and evictions).
- Pseudo-channels: `{0: 306,559, 1: 306,696}`; bank groups
  `{0: 153,274, 1: 153,192, 2: 153,320, 3: 153,469}`; all 16 banks within
  ±1 % of uniform.
- 32 distinct rows (1 MiB footprint), 453,457 request-level row switches
  (row-conflict pressure); strided segments show few switches (row locality),
  random segments (e.g. segment 5: 179,177 reqs, 134,347 switches) show heavy
  conflicts.
- HBM commands issued: **ACT 386,553 / RD 396,263 / WR 216,992 /
  PRE 386,553 / REFab 10,248** (all-bank refresh, `tREFI=4682` model cycles —
  count consistent with the ~23.9 M model-cycle span).
- No HBM timing assertion fired over the entire run.
- Simulator: Verilator metasim, 4.68 kHz effective target frequency, FMR 1.06,
  85 min wallclock.

Row locality / conflicts / bank / bank-group / pseudo-channel spreading are
all exercised by the natural streams (see per-segment stats). The pattern
parameters (`strideGrid`, `tileGrid`, `dataTypes`, `Bounded` window size,
`reqsPerPattern`) are compile-time values in `TrafficPatterns.scala` /
`MemPerf.scala`; directed row-hit/row-conflict tests would edit those (e.g.
a >32 KiB stride within one bank forces conflicts), which was intentionally
not done for this characterization run.

## 12. Multi-channel HBM (4 independent channels)

`sims/firesim` bumped to `28bbda543` (`tamzidrazzaque/firesim:hbm-modeling`),
which adds parameterized multi-channel support to the HBM timing model: one
`HBMModel` instance now elaborates `maxChannels` (default 1, this run 4)
`HBMChannelScheduler` instances, each owning its complete scheduler and
timing state (reference window, FR-FCFS row/column scheduling, PC / bank
group / bank trackers, refresh, command buses, completion pipes). Channels
share only the AXI4 front-end transaction queue and the response arbiters.
The channel select is runtime-programmable (`+mm_chAddr_offset/mask`), and
single-channel configurations are bit-identical to the previous model (all
six regression traces byte-identical; chAddr registers only exist when
maxChannels > 1).

End-to-end Radiance run: `FireSimRadianceMemPerfConfig` (unchanged target
RTL) against `PLATFORM_CONFIG=WithHBMRequestTrace_WithHBMQuadChannel_HBM2FRFCFS16GBDualPC_BaseF2Config`,
12 M base cycles, runtime config `hbm2-FRFCFS-2400-OP-REFab-4ch-radiance.conf`
(base HBM2-2400 OP/REFab plus `chAddr_offset=18, chAddr_mask=3`, i.e. a
temporary contiguous 256 KiB-per-channel partition sized so the MemPerf 1 MiB
footprint at `0x1_0100_0000` exercises all four channels; the production-shape
partition for the full 4 GiB space is `chAddr_offset=30`).

Results (vs. the single-channel run of section 6):

| Metric | 1 channel | 4 channels |
|---|---|---|
| requests accepted | 613,255 (R 396,263 / W 216,992) | 633,652 (R 405,396 / W 228,256) |
| HBM commands issued | 1,396,609 | 1,376,258 (ACT/PRE 350,807, RD 405,396, WR 228,256, REFab 40,992) |
| per-channel requests | n/a | ch0 182,502 / ch1 165,596 / ch2 142,816 / ch3 142,738 |
| request-to-channel routing mismatches | n/a | 0 of 633,652 |
| Ramulator violations | 0 | 0 (per-channel devices: 391,166 / 359,208 / 312,298 / 313,586 commands) |
| cycles with commands in >1 channel | n/a | 76,569 (all four channels simultaneously: 27,633) |
| cycles with RD/WR CAS in >1 channel | n/a | 3,173 |

Cross-channel independence was separately proven with a directed fuzzer
workload confined to (PC0, BG0, bank0): per-channel ACT-to-ACT spacing never
dropped below tRC (58 >= 57 CK), while ACTs in different channels issued as
close as the same cycle, all four channels concurrently held their
channel-local bank0 row0 open, and the same 1000-transaction stream completed
in 11,158 cycles on 4 channels vs. 30,964 on 1 (2.78x). Full methodology and
tooling live in `sims/firesim/sim/scripts/hbm-validation/`.
